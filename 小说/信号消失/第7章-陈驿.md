# 第7章 陈驿

苏晚在技术论坛泡了三天。

她把和外网那个博客文章相关的关键词全部搜了一遍：location_history_depth、地下追踪服务、订阅制追踪平台、商业化行踪监控。搜索结果里有很多垃圾信息，但她在第二页的末尾找到了一个帖子的存档链接。

帖子发布在一个程序员匿名社区，标题是：《有人知道nightwatch这个服务吗？》。

发帖时间是三年前。

她点进去，发现帖子已经被删除了，只剩下一个缓存的摘要：

```
标题：有人知道nightwatch这个服务吗？
发帖人：anonymous_9k2m
发帖时间：2022-04-15
帖子内容：
我在一家出行平台做安全工程师，最近发现我们平台的ETL管道里有一条很奇怪的规则。这条规则不是我写的，也不是我们组的代码。它的逻辑很简单，就是把is_valid=0的用户过滤掉。但问题在于，这个过滤逻辑不应该出现在ETL层，而应该在算法层。
我跟组长反映过，他让我别管了，说可能是历史遗留代码。
但我查了这条规则的创建时间，是今年4月，比公司成立还晚两年。
有没有人遇到过类似的情况？
```

苏晚把这段文字读了两遍。

发帖时间是2022年4月。三年前。比RULE_032的创建时间早了两年多。

发帖人说了一条类似的规则。但三年前的那条规则，和她现在看到的RULE_032是同一条吗？

她继续往下翻帖子。帖子的回复里有几条有意思的内容：

```
2楼：ETL层做is_valid过滤确实奇怪，正常应该在算法入口做。建议查一下这条规则的审计日志。

5楼：楼主确定不是安全测试留下的代码？有些安全测试跑完不会清理。

8楼：查了一下，这类规则一般用于数据清洗，但如果是手工写入而不是通过CI/CD发布，那就不正常了。

12楼：楼主最后怎么处理的？我也遇到类似的情况。
```

然后是楼主自己的回复：

```
15楼：谢谢大家的建议。我去找了数据组的同事，他们说这条规则是他们老大让加的，但不知道是谁写的代码。我又去找了他们老大，他让我别管了，说这件事很复杂。
我怀疑这条规则不是我们公司内部的人加的。
但我没有证据。
算了，我先换个工作。
```

苏晚盯着最后一句话看了很久。

“算了，我先换个工作。”

三年前，有人发现了类似的问题，然后选择了离职。

她根据帖子的发布时间和内容，找到了发帖人可能的技术背景。她把帖子里的代码片段单独提取出来，分析了一下代码风格。

变量命名用的是下划线分隔，函数调用用的是链式写法，错误处理用的是try-catch包裹每一层。这些都是Python的常见风格，但有一个细节引起了她的注意：作者在处理null值的时候，用了一个很罕见的写法——“if not val”而不是“if val is None”。

这种写法在数据工程师群体里不常见，但在安全工程师群体里比较常见。因为安全工程师更习惯处理布尔判断和权限校验，对null的处理方式不同于普通后端开发。

她把代码风格作为一个突破口，在GitHub上搜索了关键词组合：nightwatch、ETL过滤规则、is_valid=0。

搜索结果为零。

她又换了一个组合：nightwatch、出行平台、ETL。

这次有结果了。

搜索结果里出现了三个仓库，其中两个是英文项目，和出行平台完全无关。但第三个仓库的名字让苏晚的心跳停了一拍。

仓库名称：nw-watchdog。

创建者：crazysheep。

这个账号的GitHub主页没有任何个人信息，只有一行签名：“数据不会消失，只会在你不知道的地方流动”。

苏晚盯着这行签名看了很久。

她点开nw-watchdog仓库，发现这是一个关于数据监控的工具项目。项目不大，只有十几个star，代码结构也很简单。但README文件里有一段话引起了她的注意：

```
This project is an early attempt to monitor ETL pipeline anomalies.
It's been abandoned since I left the industry.
如果你也在出行平台工作，发现了类似的ETL异常，希望这个项目能帮到你。
——crazysheep
2022年6月
```

苏晚把crazysheep的主页翻了一遍，想找到更多信息。主页上有一个邮箱地址，是Gmail的，但被部分打码了。她只能看到前缀：chenyi_。

她又在GitHub上搜索了这个账号的其他项目。结果发现crazysheep在2022年之后就没有再活跃过，他的最后一个项目停在了2022年5月。

三年前离职，然后消失在技术社区。

她根据“chenyi_”这个前缀和“crazysheep”这个网名，在公司的离职员工数据库里查了一下。三年前的离职记录，系统里还能查到。

结果显示了一条匹配：

```
姓名：陈驿
离职时间：2022年5月
离职前岗位：安全工程师
离职前部门：技术中心-安全部
离职原因：个人发展
```

陈驿。安全工程师。2022年5月离职。

苏晚把这条记录和帖子里的信息做了对比。发帖时间是2022年4月，离职时间是2022年5月——只隔了不到一个月。

ETL规则异常。向公司反映，被无视，然后离职。

她又在内部通讯录里搜了一下陈驿的名字。结果是空白的。离职员工的账号会被系统清除，这是常规操作。

但她又查了一下陈驿离职前的项目组。他当时在安全部下面一个叫“数据安全”的小组里。苏晚把小组里其他还在职的成员名字记了下来，然后挑了一个叫张海涛的工程师，发了一封内部邮件。

邮件内容很简短：您好，我是数据部苏晚，想联系一下陈驿工程师，他之前的一个项目需要跟他确认一些细节，请问您有他的联系方式吗？

她没有抱太大期望。张海涛和陈驿是否还有联系，谁也不知道。

但当天下午，张海涛回复了邮件。

邮件里只有一个手机号码，和一句话：“他让我别联系以前的同事，但我觉得你可能真的有事找他。这个号码是他用的，我不确定还能不能打通。”

苏晚看着那个手机号码，在微信里搜索了一下。

号码的主人叫“陈驿”，微信号是一串随机的字母和数字，头像是一只黑羊的照片。

她加了好友，等了两个小时，没有通过。

她又发了一条短信到那个号码：“陈工您好，我是出行的数据分析师苏晚，我在查一条ETL规则的事情，想跟您聊聊。”

发送成功。

她又等了两个小时，手机屏幕始终是黑的。

她正准备放下手机去倒杯水，屏幕忽然亮了。

一条短信。

来自陈驿的回复：

```
你知道nightwatch是什么吗？
```

苏晚的心跳加速了。

她飞快地把U盘里的日志文件整理了一遍，把NightWatch API的调用记录截图，发给了陈驿。

她附了一句话：“姜远，去年9月30日调用过这个API，两天后失踪。”

过了很久，手机屏幕再次亮起。

这次是微信好友通过的提醒。

陈驿发来了一条语音。

苏晚点开。

声音很低，有点沙哑，像是刚睡醒或者很久没说话了：

“你从哪里拿到的这些？”

苏晚打字回复：“姜远的姐姐。他是姜远寄回家的U盘里的。”

陈驿那边沉默了几秒。

然后又来了一条语音：

“姜远还活着吗？”

苏晚的手指悬在屏幕上方，不知道怎么回答这个问题。

姜棠说姜远失踪了。警察说查不到他的下落。她没有证据证明他还活着，但也没有证据证明他已经死了。

她最终打了一行字：“我不知道。”

陈驿那边又沉默了。

过了大约一分钟，他发来了一个地址。

是一个咖啡馆的名称和位置，在光谷附近，离科技园不远。

还有一句话：

“明天晚上八点。我在那里等你。”

语音条到这里就结束了。

苏晚把手机放下，靠在椅子上，看着天花板。

三年前离职的安全工程师。发现了ETL规则异常，选择了离开。

现在，有一个数据分析师发现了同样的问题，找到了他。

陈驿愿意见她，他手里有她需要的东西。

但他也可能在试探她——或者在警告她。

苏晚不知道明天见面会发生什么。

她只知道，陈驿问了姜远是否还活着。

陈驿知道一些她不知道的事情。

关于NightWatch，关于那二十一个被过滤的用户，关于姜远。

关于那二十一个人消失之后，可能发生的事。
