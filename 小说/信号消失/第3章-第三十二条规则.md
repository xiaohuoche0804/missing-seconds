# 第3章 第三十二条规则

苏晚没有回家。

她从公司出来，在楼下便利店买了一个饭团和一罐咖啡，然后转回了办公区。保安认识她，刷卡的时候多看了她一眼，但什么也没说。这个楼层的数据分析师加班是常态，凌晨一两点走都不稀奇。

她重新坐到工位上，打开电脑。

现在她要做的事情很明确：搞清楚RULE_032的来源。

31条常规规则都有产品需求文档。她把每一条的PR链接都点开看了一遍。产品需求文档的格式很统一：需求背景、业务目标、规则逻辑、数据指标、验收标准。文档的创建者、评审人、测试报告，一应俱全。

她把31条规则的共同特征提取出来：

1. 每一条都有明确的产品经理作为需求发起人
2. 每一条都有对应的JIRA工单作为需求跟踪
3. 每一条的代码都经过至少两个人的评审
4. 每一条都有上线时间、灰发比例、回滚方案

RULE_032一条都不满足。

苏晚把31条规则的产品经理名字列了一个清单，然后对着名单在内部通讯录里搜了一圈。这31个人分布在产品、运营、数据三个部门，最早的入职工龄三年，最晚的也有一年半。

她把这31个人的名字放在脑子里转了一圈，然后开始查RULE_032的创建日志。

凌晨三点二十七分。这个时间点太尴尬了。能在这个时间点上线规则的人，要么是加班太晚顺手加的，要么是有权限绕过正常流程的。

她在后台日志系统里输入了RULE_032的规则ID。系统返回了一条记录：

```
操作者: internal_service_account
操作类型: CREATE_RULE
规则名称: RULE_032
创建时间: 2024-10-17 03:27:14
IP地址: 10.0.19.42
```

internal_service_account。

苏晚的眉头皱了起来。这个账号是公司的内部服务账号，专门给自动化工具用的，比如数据同步、报表生成、定时任务。但创建ETL规则这种操作，不应该通过这个账号来完成——常规规则的创建日志显示，操作者都是具体的员工账号。

她查了一下10.0.19.42这个IP地址。归属地是公司内网的服务器区，但不是任何一台已知的物理机器。它在内部的资产清单里找不到对应的设备标签。

要么这台"服务器"不在资产清单里，要么它根本就不是服务器——而是一个虚拟出来的地址。

苏晚把internal_service_account的权限记录调出来看了一遍。这个账号的权限列表很长，长得不太正常。它可以做数据写入，可以修改ETL管道，可以创建和删除规则，甚至可以修改其他管理员的权限。

一个给自动化工具用的服务账号，为什么需要修改其他管理员权限的能力？

她把这个问题记在心里，然后开始查RULE_032的实际代码。

ETL规则的代码存在公司的代码仓库里，仓库名称是data-etl-rules。她在仓库里搜索RULE_032，结果返回了空。

这个规则不在代码仓库里。

苏晚又搜了一次，用规则的全名、缩写、甚至创建时间戳。结果都是一样——它不在任何公开的代码库里。

她又打开了规则配置表，把RULE_032的完整信息截了图。创建时间、IP地址、服务账号，三个关键信息拼在一起，指向一个结论：这条规则不是通过正常流程上线的。它是被人直接写入数据库的。

她把RULE_032的过滤逻辑单独提取出来，放进一个测试环境里跑了一遍。

```
if (is_valid == 0) {
    return null;
}
```

逻辑很简单。如果is_valid等于0，输出null。这条规则会把所有被标记为"无效"的用户的算法评分直接过滤掉，让他们在模型里返回一个空值。

但问题在于，is_valid这个字段本身是什么时候被设置为0的？

苏晚查了RULE_032的触发时机。它不是一个主动执行的脚本，而是一个被动触发的过滤器——只要有数据流经ETL管道，就会自动被这条规则检查一遍。

只要有人在数据源头把某个用户的is_valid改成0，这个用户的算法评分就会在不知不觉中变成null。

她在系统里查了一下这二十一个用户的is_valid字段的修改记录。

结果返回了二十一条空记录。

这个字段没有被修改过。它从一开始就是0。

苏晚的咖啡呛进了气管里，她剧烈地咳了几声，眼眶有点发红。

从一开始就是0。这二十一个人在注册的时候就被打上了"无效"的标签，而不是后来被人改的。

但如果他们从一开始就是无效用户，为什么还能正常下单？为什么订单记录完整、支付记录完整、GPS轨迹完整？

除非——

苏晚忽然想到了另一种可能。

is_valid这个字段，会不会不是"账号有效性"，而是"算法有效性"？

这二十一个人在平台上的所有行为都是真实的，他们就是普通用户。但平台在算法层面把他们标记成了"无效"——不是他们本身无效，而是平台不希望他们在算法里出现。

为什么要这样做？

她还没来得及想清楚，手机屏幕亮了。

是一条内部通讯软件的消息提醒。发送者：周衍。

“苏晚，JIRA工单的事我跟算法组确认过了。RULE_032那条规则是我审批的，是之前一个数据治理项目的遗留规则，你不用管了。”

苏晚盯着这条消息，手指悬在键盘上方。

周衍说他审批过这条规则。但RULE_032的创建日志显示操作者是internal_service_account，不是周衍的账号。而且这条规则没有PR链接，没有代码评审记录，它根本就没走过正常流程。

周衍在撒谎。

或者，周衍在替别人圆谎。

她没有回复这条消息。

窗外，夜色已经很深了。远处的科技园方向，几栋写字楼的灯一盏一盏灭了。她看了看时间，凌晨两点四十七分。

RULE_032的创建时间是2024年10月17日03:27:14。

她把这个时间戳记在心里，然后开始查那天晚上公司内网的访问日志。

内网VPN的连接记录显示，10月17日凌晨三点左右，有一个内部账号通过VPN拨入了公司网络。VPN的日志里没有记录使用者的设备信息，但有一个细节：那个账号的归属部门是“技术-VPN-海外中转”。

苏晚把这条记录放大看了一遍。VPN的海外中转意味着这个人的IP出口经过了海外服务器，可能是香港，可能是新加坡，也可能是公司自建的海外节点。

技术部门。

凌晨三点。

通过海外中转登录内网。

她把这些信息整理成一个文档，存进加密的本地文件夹。然后她关掉电脑，站起身，走到窗边。

城市的夜景在眼前铺开。她想起二十一个人，想起RULE_032，想起周衍的那条消息，想起凌晨三点多的VPN记录。

有一条线把这些东西串在了一起。但她还看不清这条线的全貌。

她只看清了一个点：RULE_032不是意外。它是被人放进来的。

而且它被放进来的方式，几乎是在明示——有人在故意留下痕迹。

苏晚看着窗外，拿起手机看了一眼自己整理的那个文档。

创建时间，精确到秒。2024-10-17 03:27:14。

这个精确度不像是随手敲的。它像是故意留下的。

像是一个署名。

她把手机放回口袋，拿起包，准备离开。

电梯下行的时候，她忽然想起周衍消息里那句话：“你不用管了。”

周衍知道这条规则存在。他甚至可能知道这条规则是谁建的。但他选择压下来。

苏晚在电梯里站了一会儿，然后走出大楼，走进夜色里。

她知道自己不会停下来。

RULE_032是一条线索，周衍是一条线索，那二十一个用户也是一条线索。

她现在手里有三个线索，它们指向同一个方向。

但那个方向是什么，她还需要更多的东西才能看清。
