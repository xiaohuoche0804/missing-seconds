# 第6章 代码之外

苏晚把U盘里的日志文件翻来覆去看了三遍。

nightwatch_svc的API调用记录显示,它在姜远失踪前三天被调用了七次。每次调用的请求参数都一样:target_id是姜远的乘客ID,location_history_depth是full,scope是realtime。

Full和realtime。这两个词放在一起,意味着NightWatch不是查当前位置,而是要求获取目标的完整历史轨迹。

一个内部服务,为什么需要调用"完整历史轨迹"这种参数?

苏晚在公司内网的开发者门户里搜索了nightwatch_svc。返回结果是零。她又试了大小写变体、缩写、甚至拼写错误,结果都一样。

这个服务在内部没有任何文档。

她想起姜远的日志文件里有七个调用记录,每一个都有完整的请求和响应。她把第七条记录单独调出来看。

```
[2024-09-30 14:29:47] nightwatch_svc API called
Endpoint: /v2/track
Request: {"target_id":"P_5591044728","location_history_depth":"full","scope":"realtime"}
Response: {"status":"success","location":"30.5782,114.2917","accuracy":"15m","timestamp":"2024-09-30T14:29:47Z","additional_info":{"target_name":"姜远","device_id":"xiaomi_13_8T5K92","last_seven_days_poi":["科技园C栋","光谷大道星巴克","光谷广场地铁站","星火苑小区","科技园地下停车场"]}}
```

最后七天的POI点。姜远的行踪被完整地记录了下来。

苏晚盯着这行数据,后背有点发凉。

NightWatch不只是一个追踪服务。它是一个数据库,里面存着用户的完整出行轨迹。它可以查询任意一个平台账号的实时位置,也可以调取这个账号过去七天的所有出行记录。

这种数据量不是普通的内部工具能支撑的。它需要存储、计算、实时更新--这不是一个功能模块,这是一套系统。

她在内网的服务器资产清单里搜索"nightwatch"。结果还是零。

她又换了一个思路,去查姜远那七次API调用的来源IP地址。

日志文件里没有记录调用来源,但她查了姜远那台小米手机的登录IP。10月3日下午三点十七分,姜远登录平台的时候,使用的是哪个IP地址?

她调出那天的登录记录,IP地址赫然显示:10.0.19.42。

苏晚的呼吸停了一秒。

10.0.19.42。RULE_032的创建IP地址。

同一个IP地址。一个在凌晨三点多创建设置过滤规则,一个在下午三点多查询用户位置。

这不是巧合。

这两个操作使用的是同一台服务器,或者至少是同一个网络节点。

她把10.0.19.42这个IP单独拿出来查。这台设备在公司内网的资产清单里没有登记,但在防火墙的流量日志里有记录。

她翻出防火墙日志,找到了10.0.19.42的流量记录。

这台IP在过去半年里有过大量的外部连接。它的出口流量去向了几个陌生的IP段,不是公司任何一个业务线的服务器地址,也不是已知的云服务商地址段。

她把这些IP段记下来,然后继续往下查。

她又查了RULE_032的创建时间戳。2024年10月17日03:27:14。

她把姜远的API调用时间和RULE_032的创建时间做了一个对比。姜远的第一次调用是去年9月30日,比RULE_032的创建时间晚了三个多月。

这意味着RULE_032不是专门为姜远设置的。它在这二十一个人被过滤之前就已经存在了。

她把二十一个用户的名单调出来,逐一查了他们第一次触发RULE_032过滤的时间。结果很有意思:

最早的一个是去年11月8日,最晚的一个是去年10月3日。RULE_032从创建之后就开始运作,一直持续到姜远消失的那天。

苏晚把时间轴串起来想了一遍。

去年10月17日,RULE_032被创建,通过10.0.19.42这个IP,从internal_service_account写入数据库。

去年11月8日,第一个用户被过滤。

去年9月30日，姜远开始调用NightWatch的API。

去年10月3日，姜远最后一次登录平台。

去年10月——姜远失踪。

她把这些时间点写在白板上,看着它们排成一列。

有一条线把这些时间点串在一起:10.0.19.42。

这台不存在的服务器,既创建了过滤规则,又接收了姜远的API查询请求。

她继续查10.0.19.42的外部连接记录。她把时间范围拉长到过去一年,结果发现这台IP第一次出现是在去年9月。

去年9月。RULE_032创建前一个月。

她把9月的连接记录单独导出来看。结果发现了一个有意思的数据:9月15日到9月20日之间,10.0.19.42有过一波密集的外部连接。连接目标是同一个IP段,连接频率是每分钟几十次,持续了五天。

然后在9月20日之后,连接频率骤降,变成每天几次。

她在脑子里把这些信息拼成一个场景:有人在去年9月搭建了一台服务器,10月用它创建了RULE_032,然后这台服务器从11月开始,一直在执行过滤任务。

但这台服务器不在公司的资产清单里。

这意味着两件事:要么它是用虚假信息登记的,要么它根本不是通过公司流程部署的。

无论哪种情况,都指向同一个结论:部署这台服务器的人,有能力绕过公司的正常IT管理流程。

苏晚靠在椅背上,揉了揉太阳穴。

她已经连续查了三天,U盘里的信息量很大,但她需要时间消化。

她决定先把NightWatch的事情放一放,去查另一个线索:RULE_032的代码仓库。

RULE_032不在data-etl-rules仓库里,但它肯定有代码。她在公司的代码托管平台GitLab上搜索了nightwatch关键字,结果返回了一个私有仓库。

仓库名称是nw-svc,访问权限显示:需要管理员授权。

苏晚试着用自己的账号访问,结果返回了403。

她又查了一下这个仓库的基本信息。创建时间是去年9月15日，创建者是一个叫"system_init"的账号。仓库的最近一次提交是去年9月28日。

姜远失踪前两天。

她把nw-svc这个仓库名记下来,然后继续查system_init这个账号。

账号信息显示这是一个系统账号,创建时间是公司成立之初。它的职责描述是"基础设施初始化",没有对应的员工信息。

她查了这账号的权限范围。结果让她倒吸了一口凉气。

system_init拥有公司GitLab上所有私有仓库的访问权限,包括核心业务代码、基础设施配置、甚至HR系统的人才数据库。

一个挂着"基础设施初始化"头衔的系统账号,拥有几乎无限的代码访问权限。

它创建了nw-svc仓库,创建时间是去年9月15日--和10.0.19.42第一次出现的时间完全一致。

苏晚把这些信息整理成一个文档,然后打开了公司内网的代码平台,搜索nw-svc。

还是403。

她没有管理员权限,碰壁是意料之中的事。但她需要知道那个仓库里的代码长什么样。

她换了一个思路。

公司在代码平台上有一个"最近活跃的仓库"列表,这个列表对所有员工可见。她把这个列表导出来,从第一页翻到第十页,没有找到nw-svc。

这意味着nw-svc不在活跃列表里。或者,它被从列表里隐藏了。

她又试了另一个方法:去DNS查询工具里查nw-svc的仓库域名解析。

如果nw-svc是一个内部服务,它应该有一个内部DNS地址。她在公司的DNS日志系统里搜索了"nw-svc"、"nightwatch"、"nightwatch-svc"等关键词。

结果全部是空。

她没有放弃,换了一个思路:去查姜远那七次日誌文件里NightWatch API的完整Endpoint。

姜远的日志显示Endpoint是/v2/track,但她不知道服务器地址。她在外网的搜索引擎里查了一下"/v2/track nightwatch",结果返回了一些无关的内容。

她又尝试搜索nightwatch_svc的具体信息。这一次,她没有直接搜服务名,而是搜索了日志文件里出现的一个参数:"location_history_depth=full"。

这次有结果了。

外网上有一个技术博客,文章标题是《暗网追踪服务的API参数分析》。文章里提到了location_history_depth这个参数,描述是:"用于获取目标完整历史轨迹的隐私侵犯参数,常见于地下追踪服务"。

苏晚把博客文章的链接点开,快速浏览了一遍。

文章里提到,location_history_depth是一个非公开参数,只在少数追踪服务的API文档里出现。这些服务大多是商业化的个人行踪监控工具,面向企业客户,销售"员工外勤管理"或"家人安全守护"等产品。

文章没有提nightwatch_svc这个名字,但它提到了另一个关键词:"订阅制"。

这类服务通常采用订阅制,年费从几千到几万不等,取决于追踪的目标数量和数据精度。

苏晚盯着"订阅制"这三个字看了很久。

订阅制意味着有稳定的客户群。稳定的客户群意味着这不是一个试验性的项目,而是一个已经商业化运营的服务。

她在脑子里把这条信息和RULE_032的时间线对上。

去年9月,nw-svc仓库创建。去年10月,RULE_032上线。去年10月,姜远发现NightWatch的存在并调用了它的API。然后姜远失踪。

苏晚合上电脑,靠在椅背上。

NightWatch不是公司内部的免费工具。它是对外收费的商业服务。

而RULE_032,是把目标用户从平台算法里过滤掉的工具。

这两件事结合起来,指向一个她不愿意相信但又无法否认的结论:

有人在用"出行的士"的平台数据,为一个外部的商业追踪服务提供目标筛选。

那二十一个被过滤的用户,不是随机挑选的。他们是NightWatch的客户想要追踪的人。

而NightWatch的客户是谁,她还不知道。

她站起身,走到窗边。城市的灯火在远处闪烁,夜色已经很深了。

她想起姜棠说的话:姜远失踪前一周每天都去科技园,他说他在帮一个朋友查一些东西。

帮朋友查东西。他发现了NightWatch的存在。他调用了它的API,查到了自己的行踪。

然后他就失踪了。

苏晚把U盘从口袋里拿出来,放在桌上。

U盘里的日志文件是姜远留给她的线索。nw-svc仓库是NightWatch的代码所在。RULE_032是过滤工具,10.0.19.42是执行服务器。

她现在有了四条线索,它们都指向同一个方向:

那二十一个人,是NightWatch的追踪目标。

而NightWatch的客户,藏在某个她还没有找到的地方。
