# 第9章 猫鼠游戏

苏晚周一早上到公司的时候,发现自己的数据库访问权限变窄了。

她习惯性地打开SQL客户端,输入上周的查询语句,结果返回了一条错误:

```
ERROR 1143: User 'suwan' does not have SELECT permission on table 'orders_all'
```

orders_all表是她查那二十一个人数据的主表。她上周还用这个表跑过查询,今天就没权限了。

她联系了数据组的同事张工。张工查了一下后台,回复她说:"苏晚,你的权限被调整了,理由是数据安全审计。orders_all表的访问权限已经从你的角色里移除了。"

苏晚问:"谁调整的?"

张工回:"不知道,审批记录显示是自动化任务触发的。"

自动化任务。又是这个词。

苏晚挂断电话,打开了权限变更的审计日志。

日志显示权限变更的操作时间是凌晨三点十七分。操作类型是"自动化安全扫描触发"。触发条件是"关键词:nightwatch"。

苏晚的血液在一瞬间变凉。

有人设置了触发器。只要有人在系统里搜索nightwatch相关的关键词,就会自动触发权限收缩。

而且触发时间是凌晨三点十七分。

RULE_032的创建时间是凌晨三点二十七分。

10.0.19.42的活跃时间集中在凌晨三点左右。

凌晨三点,这是一个特殊的时间窗口。系统管理员在线率最低,安全审计覆盖率最差,异常操作最难被发现。

苏晚意识到,她已经被盯上了。

她查了nightwatch的关键词是什么时候进入触发条件的。审计日志显示这个触发器是在昨天晚上十点四十二分创建的。创建者是system_init。

又是system_init。

她现在失去了orders_all表的访问权限,但她之前已经导出了那二十一个用户的完整数据。这些数据存在她本地的加密硬盘里,权限收缩影响不到她。

但她的查询通道被堵死了一半。

苏晚靠在椅背上,盯着天花板想了几分钟。

她有一个备份管道。

这是她做数据分析师养成的习惯。重要的查询任务她会设置定时同步,把结果备份到另一个数据源,以防主数据源出现故障。这个备份管道用的是公司的公共数据集接口,绕过了她个人的权限限制。

她打开备份管道的配置文件,把那二十一个用户的ID列表输了进去。

十五分钟后,备份数据同步完成。

数据完整。订单记录、出行轨迹、支付流水,一样不缺。

苏晚把数据导出来,开始重新分析。

她先查了这二十一个人在失去平台访问权限之前,有多少人试图登录过平台。

结果让她愣了一下。

二十一个人里,有七个人在算法过滤之后还尝试过登录平台。他们的登录时间集中在去年十月初到十月中旬,但全部以失败告终--系统提示"账号状态异常"。

这七个人在算法过滤之后意识到了自己无法正常使用平台,然后试图登录查看发生了什么。

她又查了这七个人的登录设备信息。

其中两个人的登录设备发生了变化--他们用新设备尝试登录,但没有成功。剩下五个人的登录设备没有变化,但他们登录失败之后就再也没有尝试过。

苏晚把这七个账号单独标记出来,开始查他们的用户画像。

结果发现了一个异常:这七个账号的用户画像在过滤前一个月内发生过一次大规模更新。

以其中一个账号为例,用户画像他在过滤前一个月内更新过职业信息--从"自由职业"改成了"企业主"。消费等级从"中等"上调到"高"。常去区域从"城区"扩展到"科技园区"。

这个更新模式很奇怪。一个普通用户,为什么会在一个月内突然改变自己的出行标签?

她又查了其他六个账号的用户画像更新记录。结果发现了一个共同特征:这七个账号的用户画像更新,都发生在他们对NightWatch进行反向查询之前。

苏晚把时间线整理出来:

第一步:用户在平台上积累了大量真实的出行数据。
第二步:NightWatch的订阅客户把这些用户设为追踪目标。
第三步:用户的出行数据被RULE_032复制到NightWatch的数据库。
第四步:用户发现自己被追踪,试图查询自己的数据。
第五步:用户的画像被更新--标记为"高价值目标"或类似标签。
第六步:用户的账号被过滤,从平台算法里消失。

她不确定第五步和第六步的逻辑是什么。但她意识到,用户画像的更新可能是某种内部警报机制--当被追踪目标开始主动查询自己的数据时,系统会标记他们,并启动下一步处理。

她在脑海里把这套流程过了一遍,然后打开权限变更的日志。

触发条件是关键词nightwatch。她的查询记录里有这个词。所以她的权限被收窄了。

但触发器是昨天晚上十点创建的。

她在想:是谁知道她查了nightwatch?是谁在监控她的查询行为?

答案只有一个:有人在她之前设置了触发器,然后等待关键词出现。

这是一个防守机制。当有人在系统里搜索nightwatch,就会自动触发权限限制。--

她在想:这个触发器是专门为她设置的吗?

不对。触发器是昨天晚上十点创建的,而她查nightwatch是在三天前。

如果触发器是专门针对她的,不会等三天才生效。

除非触发器不是针对她,而是针对所有可能的关键词搜索者。她只是碰巧撞上了枪口。

苏晚把权限变更的审计日志仔细看了一遍。

触发条件是nightwatch,但触发器本身在创建的时候指定了一个白名单--在这个白名单里的人搜索nightwatch不会触发权限变更。

她查了一下白名单的内容。

结果是空的。没有任何账号在白名单里。

这个触发器是一个无差别触发。任何人在任何时候搜索nightwatch,都会被收窄权限。

这个触发器不是为了防她。

它是为了防止任何人接近NightWatch。

苏晚合上电脑,靠在椅背上。

她意识到一件事:她不是这场游戏里的猎人。她从一开始就是猎物。

有人在暗处看着她,看着她一步一步挖出nightwatch的存在,看着她一步一步接近真相。

然后在她即将触及核心的时候,收紧了绳子。

但她也意识到另一件事:收紧绳子的人,没有直接对她动手。

对方在顾忌什么。或者对方认为她还不够重要,不值得动用更激烈的手段。

她还有机会。

她站起身,走到茶水间,给自己倒了一杯水。路过窗户的时候,她看到楼下停车场有一辆黑色的商务车停在那里,车窗贴着深色膜,看不清里面。

她站在窗边喝完水,然后回到工位。

她需要换一种方式继续查。

她的权限被收窄了,但她的备份管道还在。她可以继续从备份管道里拉取数据,不需要直接访问主数据库。

但她需要更多的信息。

她打开手机,给陈驿发了一条消息:"我的权限被收了。"

过了十分钟,陈驿回复了三个字:"正常的。"

苏晚又发了一条:"你知道是谁设置的吗?"

这次等了更久。大约半小时后,陈驿的回复来了:

"别查了。"

苏晚盯着这两个字看了很久。

她没有回复,而是把手机放回桌上,继续做自己的分析。

她查了那七个在过滤后尝试登录平台的用户的登录失败原因。系统提示都是"账号状态异常",但具体的错误代码各有不同。

她把这七个错误代码单独提取出来,发现其中五个错误代码是同一个:ERR_ACC_SUSPENDED。另外两个错误代码是ERR_ACC_FROZEN。

ERR_ACC_SUSPENDED是账号被暂停。ERR_ACC_FROZEN是账号被冻结。

她查了这两个错误代码的处理流程。

ERR_ACC_SUSPENDED通常是由于用户投诉或风控警报触发的,需要人工审核才能恢复。ERR_ACC_FROZEN通常是由于司法调查或高级别风控触发的,解冻需要更高权限。

她注意到一个细节:那五个触发ERR_ACC_SUSPENDED的账号,状态是"暂停",不是"删除"。暂停的账号在数据库里还有记录,只是被标记为不可用。但那两个触发ERR_ACC_FROZEN的账号,状态是"冻结"--冻结是比暂停更高级别的处置。

她把那两个冻结账号的信息单独调出来。

其中一个账号的用户名是姜远的。

姜远的账号不是被暂停,而是被冻结。

苏晚把这两个人--姜远和另一个冻结账号的用户--做了对比分析。

两个人的共同点:第一,都是在算法过滤后尝试登录平台的。第二,登录失败后的状态都是冻结。第三,两个人的最后登录时间相差不到一周。

她查了另一个冻结账号的用户画像。结果发现这个人是一个三十七岁的男性,注册时间是2023年11月,账号被冻结的时间是去年10月10日。

去年10月10日。比姜远失踪晚了七天。

姜远是10月3日最后一次登录，10月10日账号被冻结。七天后。

另一个用户是10月6日最后一次登录，10月10日账号被冻结。四天后。

苏晚盯着这两个时间差,发现了一个规律。

算法过滤发生在最后行程之后的72小时。账号冻结发生在用户尝试登录之后的4到7天。

从过滤到冻结,中间大约有一周左右的窗口期。

这一周里发生了什么?

她在脑海里过了一遍:用户最后行程 → 72小时后算法过滤 → 用户发现自己无法正常使用平台 → 用户尝试登录 → 登录失败 → 4-7天后账号被冻结。

这是一个处置链条。每一个环节都有时间间隔,不是立刻执行的。

什么?

系统是分阶段处置的。每一次处置之间有等待期。

等待期是用来做什么的?观察吗?

苏晚想起陈驿说的话:三年前有人被追踪,然后消失了。

消失之前,有没有人试过登录平台?有没有人在算法过滤之后试图找回自己的账号?

她不知道答案。

她只知道,从算法过滤到账号冻结,中间有一周的时间窗口。

而她的权限被收紧,就发生在这个窗口期内。

这不是巧合。

苏晚把手机拿起来,给陈驿发了一条消息:"姜远的账号是什么时候被冻结的?"

这次陈驿的回复很快："10月10日。"

"冻结的原因是什么?"

陈驿那边沉默了很久。

然后他发来一条语音。

苏晚点开。

声音很低,像是刻意压着嗓子说的:

"因为他查到了客户名单。然后系统检测到了。"

苏晚听完,把手机放下。

她终于明白了。

算法过滤不是最终目的。过滤是为了让目标用户从平台消失,让他们无法正常使用服务。

但如果目标用户在消失之前尝试查询自己的数据,系统就会升级处置--冻结账号。

这是为了防止他们接触到更多的东西。

姜远就是在第5步--查询自己的数据--被升级处置的。

而她,现在正在重复姜远做过的事。

她的权限被收紧,就是升级处置的第一步。

苏晚把手机攥在手里,盯着屏幕上的对话框。

陈驿说别查了。

她知道他说的是对的。查下去会出事。姜远就是例子。

但她也意识到另一件事:陈驿还活着。他三年前发现问题,选择离开,到现在还活着。什么?

说明只要不触及核心,系统不会主动动手。

她现在触及了什么?权限收紧意味着她已经被盯上了,但她还没有被冻结。

她还有行动空间。

她站起身,走到窗边。

楼下的黑色商务车还停在那里。她不确定是不是巧合。

她需要做一件事:找到一个安全的通讯方式,和陈驿共享更多信息。

陈驿用的是加密通讯软件,他的微信号被隐藏了。但他昨天在咖啡馆里跟她说了那么多,说明他也在犹豫--他想说出来,但他又害怕。

苏晚想了想,给陈驿发了一条消息:

"今天下午五点,我发你一个东西。你看完告诉我怎么看。"

陈驿那边没有回复。

但苏晚知道他会看的。

她把手机放下,回到工位,开始整理她要发给陈驿的东西。

那七个账号的完整数据--从算法过滤到账号冻结的全流程记录。

还有那二十一个用户的名单,和NightWatch订阅客户的截图。

她把这些东西加密打包,设置了定时发送。

然后她合上电脑,等待下午五点的到来。

窗外的阳光很好,但她感觉不到温度。

她知道她在做的事情很危险。

但她也知道,她已经没有退路了。

她正在接近那个核心。

那个让姜远消失的核心。

但有些时候——比如现在——她会隐约觉得，她不是在接近真相。而是真相在引导她走过去。每一步都像是被人提前铺好的。
