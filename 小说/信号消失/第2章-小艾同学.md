# 第2章 小艾同学

第二天早上九点十五分，苏晚比平时早到了四十五分钟。她在茶水间泡了一杯美式，端着杯子坐到工位上，打开电脑的第一件事是调出昨天那张二十一个ID的列表。

她随机选了排在第一位的用户，点进去看详细信息。

乘客ID：P_8927410563。注册时间：2023年6月12日。最近一次订单：去年10月17日，凌晨两点四十三分。行程起终点：高新区软件园——星火苑小区。支付方式：微信支付。行程状态：已完成。

苏晚在后台系统里搜了一下这个ID的用户名。注册名叫“艾小蕾”，但订单标签里有一个网名备注：“小艾同学”。

她把这个人单独拖进一个筛选框，开始查她所有的历史订单。

一共二十三笔。最早的一笔是2023年6月13日，从城东老校区到市中心医院。最晚的一笔就是去年10月17日凌晨那笔，从高新区软件园回星火苑。

苏晚把这些行程数据导出，做了一张简单的散点图。横轴是时间，纵轴是行程距离。

大多数点都集中在城市中轴线附近，零星分布，没有规律。但有两段时间出现了明显的聚集——去年九月中旬到十月中旬，以及去年十一月中旬到十二月中旬。

她把这两个时间段标红，发现它们有一个共同特征：出发地或者目的地都包含同一个坐标点，高新区软件园。

苏晚靠在椅背上，盯着屏幕发了会儿呆。

高新区软件园。她在脑子里调取了一下那张地图。那里聚集了十几家科技公司，还有一些创业孵化器，是这两年城市向东发展的重点区域之一。

“小艾同学”从去年九月中旬开始在软件园附近频繁出没，持续到去年十月中旬，然后突然从系统里消失了。

不是注销账号——注销账号会留下记录，算法模型对注销用户有专门的标签处理。这个人是直接被is_valid=0过滤掉的，像从来没存在过一样。

苏晚打开公司内部的用户画像系统，试图查看“艾小蕾”的完整画像标签。结果系统返回了一个大大的灰色“暂无数据”。

她又试了试订单详情页——可以打开，但用户画像那一栏是空白的。性别、年龄段、消费等级、活跃度，所有字段都是系统默认值。

一个使用了平台二十三次、注册将近两年的活跃用户，用户画像全是默认值。

这不正常。用户画像系统是自动打标的，只要有过订单行为，就会生成对应的标签。除非——这些标签被人删掉了。

苏晚的手指悬在键盘上方，停顿了几秒，然后打开了JIRA工单系统。

她创建了一个新工单，标题写的是“异常用户数据查询请求”，描述里写了她发现的问题：某批次用户ID在算法模型中返回null，数据完整但is_valid标记异常，疑似数据管道故障，申请算法组协助排查。

她把工单的优先级选成了“低”。

这是她故意的。高级别的工单需要层层审批，还要写明业务影响，她不想在没有搞清楚之前把事情闹大。低优先级的工单响应慢，但至少不会被直接打回。

提交完工单，她给自己又倒了一杯水，然后靠在工位隔板上，等着。

JIRA的响应速度她有数，低优先级工单平均处理周期是七十二小时。她有足够的时间继续自己查。

但她低估了系统自动分发机制的效率。

下午三点四十二分，她的工位电话响了。来电显示：算法组-周衍。

苏晚接起来。

“苏晚？”对面是一个略带沙哑的男声，“我是算法组的周衍，你的JIRA工单我看了。”

“周总。”苏晚下意识坐直了身体。周衍是技术总监，底下管着算法组和数据组，她平时没什么机会直接和他对话。

“低优先级，但你写的描述像是高优先级的语气。”周衍的声音听不出情绪，“我让底下人跑了一下你列的那批ID，确实有你说的现象。但我看了他们返回的分析结果，系统显示这批用户在去年十二月有一次统一的数据清洗操作，清洗原因是'异常账号冻结'。”

苏晚愣了一下。

异常账号冻结？她的查询结果显示这些账号的状态都是正常的啊，订单记录完整，支付记录完整，没有一条显示“冻结”。

“周总，我查过这些账号的状态，”她说，“都是正常的，没有冻结记录。”

对面沉默了两秒。

“我再让他们查一下。”周衍的语气有了一丝变化，“你先别动这个了，我去问算法组要详细的数据清洗日志。”

“好的，麻烦周总了。”

挂断电话，苏晚盯着电脑屏幕，心里隐隐觉得哪里不对。

周衍说这些账号在去年十二月被统一冻结过。但她在订单系统里查到的最新订单是去年十二月。一个被冻结的账号，怎么还能继续下单？

除非要么周衍在撒谎，要么系统里有人篡改了记录，要么——

苏晚忽然想起一件事。

她查的是订单表。订单表的数据来源是算法模型的输出。如果算法模型本身被动了手脚，输出层的数据可以是“正常”的，但模型背后的原始数据已经被修改过了。

她昨天在算法模型日志里看到的is_valid=0，会不会不是“被过滤”，而是“被标记”？

苏晚打开ETL规则配置表，把鼠标滚轮往下拉。屏幕上跳出一行行数据清洗规则，编号001到031，每一条都有明确的业务负责人、产品需求文档链接、以及代码评审记录。

她逐条往下看。这31条规则涵盖了订单状态异常、支付失败、GPS坐标偏移、用户投诉标记等常见场景，每一条的逻辑她都能看懂。

看到第31条的时候，她的目光顿住了。

第32条规则。

她的眼睛眯了起来。

屏幕上确实有一条第32条规则，编号RULE_032，名称标注的是“冗余字段清理”，创建时间是2024年10月17日。但往下看，Owner一栏是空的。产品需求文档链接一栏是空的，代码评审记录也是空的。

一条没有任何标注的孤立规则，夹在正常的31条规则中间。

苏晚把这条规则的详细内容展开。

```
RULE_032: 冗余字段清理
条件: is_valid = 0
处理: 过滤输出，标记为null
创建时间: 2024-10-17 03:27:14
Owner: [空]
PR链接: [空]
审计人: [空]
```

她把这条规则的逻辑记在心里，然后关掉页面。

is_valid=0，过滤输出，标记为null。

这条规则创建的时间是去年十月十七日。而那二十一个用户的订单，从十一月才开始出现异常。

时间线上刚好衔接。

苏晚看着屏幕，手指无意识地敲着桌面。

31条规则，每一条都能追溯到具体的产品需求和代码评审。唯独第32条，没有人知道它是怎么来的，也没有人知道是谁创建的。

凌晨三点二十七分。

这个时间戳让她打了个寒颤。

她看了看窗外。天已经黑了，办公区只剩下安全出口的指示灯亮着。她把电脑合上，收拾东西，准备回家。

但脑子里那条孤零零的RULE_032一直在转。

它不属于任何产品需求。它没有代码评审记录。它的创建时间是凌晨三点多。

它过滤掉了二十一个用户，让他们从算法模型里消失，变成null。

苏晚走进电梯，按下负一层的按钮。

她想起周衍挂断电话前的那句“我再让他们查一下”。周衍的语气里有变化，但不是惊讶，更像是……确认。

她不确定这意味着什么。

电梯门开了，苏晚走出去，城市的灯光在头顶上连成一片。

第32条孤立规则。它就像一条缝在衣服内侧的线，不打开看，永远不知道里面藏着什么。

她已经打开看了一眼。

现在她想知道，这条线通往哪里。
